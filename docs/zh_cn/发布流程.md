# 发布流程

发布相关定义在 `.github/workflows/`。产物名前缀、Mirror酱开关和 changelog 仓库地址仍是模板占位，行为以下面的 YAML 为准。占位清单见 [模板遗留与待改进](模板遗留与待改进.md)。

模板 README 要求发布前把仓库的 Actions 权限改成读和写：`Settings` → `Actions` → `General` → `Workflow permissions` → `Read and write permissions`。`release` 作业要用 `GITHUB_TOKEN` 创建 GitHub Release。

## check

文件：`.github/workflows/check.yml`。

触发条件：

- 推送到任意分支，或针对任意分支的 Pull Request，且改动了 `.github/workflows/check.yml`、`assets/**` 或任意 `**.py`
- 手动 `workflow_dispatch`

作业 `resource` 在 `ubuntu-latest` 上依次执行：

1. `actions/checkout@v4`，`fetch-depth: 0`
2. Node 22
3. `npx @nekosu/maa-checker@latest ./assets/interface.json --github=.`
4. `pip install --upgrade maafw --pre`，再运行 `python ./check_resource.py ./assets/resource/`
5. 安装 `jsonschema==4.26.0` 和 `referencing==0.37.0`，再按 [本地开发与调试](本地开发与调试.md) 里的参数运行 `tools/validate_schema.py`

这条工作流不下载 OCR 模型，也不打包。

## install

文件：`.github/workflows/install.yml`。这是实际产出安装包和 GitHub Release 的工作流。

触发条件：

- 推送匹配 `v*` 的 tag
- 推送到任意分支，或针对任意分支的 Pull Request，且改动了 `.github/workflows/install.yml`、`assets/**` 或任意 `**.py`
- 手动 `workflow_dispatch`

只有 tag 推送会创建 Release。分支推送和 Pull Request 在路径匹配时仍会打包并上传 Actions 产物，但 `release` 作业的条件是 `is_release == true`，不会发版。

### 版本号

作业 `meta` 先执行 `git describe --tags --match "v*"`。

- `github.ref` 以 `refs/tags/v` 开头时，`is_release=true`，版本号保持 `git describe` 的结果（打在该提交上的 tag 本身，例如 `v1.0.1`）
- 分支或 Pull Request 上，只要仓库历史里已有 `v*` tag，`git describe` 就会得到 `<tag>-<提交数>-g<短 SHA>`，这一结果已经以 `v` 开头，不会再去请求 GitHub API。本仓库当前有 tag `v1.0.1`，所以分支构建会落在这条路径上。因为不是发版，脚本再用 `${tag%-*-*}` 去掉末尾两段，把版本改写成 `v1.0.1-ci.<提交数>-g<短 SHA>`
- 只有 `git describe` 没有得到 `v*` 开头的结果时，才请求本仓库最新 Release 的 `tag_name`；请求失败或结果仍不是 `v*` 则用 `v0.0.0`。然后拼成 `<该 tag>-<年月日>-<短 SHA>`，再按同样规则改成 `<该 tag>-ci.<年月日>-<短 SHA>`

tag 文本匹配 `alpha`、`beta`、`rc`、`dev` 或 `-ci` 时，`is_prerelease=true`。带 `-ci.` 的分支构建因此算预发布。

这个版本字符串会传给 `tools/install.py`，写入安装目录里 `interface.json` 的 `version`。源码里的 `version`（当前 `1.0.2`）不会被这次运行改掉。

### 矩阵打包

作业 `install` 依赖 `meta`。矩阵是 4 个系统乘 2 个架构，`fail-fast` 为 `false`：

- `os`：`win`、`macos`、`linux`、`android`
- `arch`：`aarch64`、`x86_64`

每个组合：

1. `actions/checkout@v4`，并拉取子模块
2. 用 `robinraju/release-downloader` 下载 `MaaXYZ/MaaFramework` 最新 Release 里匹配 `MAA-<os>-<arch>*` 的文件，解压到 `deps/`
3. 非 Android：同样下载 `SweetSmellFox/MFAAvalonia` 最新包，文件名里的系统写为 `win` / `osx` / `linux`，架构写为 `x64` / `arm64`，解压到 `MFA/`，删掉压缩包，再删掉 `MFA/runtimes`
4. 非 Android：若存在 `MFA/`，用 `rsync -av --ignore-existing` 拷进 `install/`
5. 在 `tools/` 安装 `requirements.txt`，执行 `python ./install.py <tag> <os> <arch>`
6. 用 `actions/upload-artifact@v4` 上传整个 `install/`，产物名是 `MaaXXX-<os>-<arch>`

`install.py` 的拷贝规则见 [本地开发与调试](本地开发与调试.md)。桌面平台会再把 `deps/bin/plugins` 放到 `install/plugins/<dotnet-rid>/`，把 `MaaAgentBinary` 放到 `install/libs/MaaAgentBinary/`。Android 把 `MaaAgentBinary` 放到 `install/MaaAgentBinary/`，并且不打包 MFAAvalonia。

### 更新说明和 GitHub Release

作业 `changelog` 使用 `orhun/git-cliff-action@v4`，配置文件是 `.github/cliff.toml`，参数为 `-vv --latest --strip header`。正式版（`is_prerelease` 为 false）额外加上 `--tag-pattern "^v[0-9]+\\.[0-9]+\\.[0-9]+$"`，让说明包含自上一个严格三位版本号以来的提交。预发布版只包含自上一个 tag 以来的提交。

`cliff.toml` 按约定式提交前缀分组，例如 `feat`、`fix`、`docs`。提交说明或正文含 `[skip changelog]` 的提交会跳过。`[remote.github]` 仍写着 `owner = "MaaXYZ"`、`repo = "MaaPracticeBoilerplate"`，生成的链接会指向模板仓库。

作业 `release` 仅在 `is_release` 为 true 时运行。它下载全部产物到 `assets/`，对每个产物目录执行：

```bash
(cd "$f" && zip -r "../$f-${tag}.zip" .)
```

得到的文件名形如 `MaaXXX-win-x86_64-v1.0.0.zip`。随后 `softprops/action-gh-release@v2` 上传 `assets/*`，`tag_name` 用上面算出的 tag，正文用 changelog，`draft` 为 false，`prerelease` 与 `is_prerelease` 一致。

工作流末尾有一个触发 Mirror酱上传的步骤，条件写的是 `if: false`，不会执行。注释里的原条件是 `github.repository_owner == 'MaaXYZ'`。

打正式版 tag 的命令在模板 README 里是：

```bash
git tag v1.0.0
git push origin v1.0.0
```

tag 需要匹配工作流的 `v*`。

## Mirror酱

下面两个工作流的作业条件都是 `if: false`，推送和手动触发都不会真正上传。

| 文件 | 触发 | 现状 |
| --- | --- | --- |
| `mirrorchyan_release.yml` | 仅 `workflow_dispatch`，输入 `tag` | 注释掉了 `release: types: [released]`。矩阵是 `win` / `macos` / `linux` 乘 `aarch64` / `x86_64`，在 `macos-latest` 上调用 `MirrorChyan/uploading-action@v1` |
| `mirrorchyan_release_note.yml` | `workflow_dispatch`，以及 Release 被 `edited` | 调用 `MirrorChyan/release-note-action@v1` |

两个文件里的 `mirrorchyan_rid` 都是 `MaaXXX`，`owner` 是 `MaaXYZ`，`repo` 是 `MaaXXX`。上传 token 读取 `secrets.MirrorChyanUploadToken`。`interface.json` 里的 `mirrorchyan_rid` 和 `mirrorchyan_multiplatform` 同样被注释，注释写明新项目默认关闭，需要联系 Mirror酱开通后才能使用。

## Schema 同步

文件：`.github/workflows/sync_schema_files.yml`。

触发：每天 UTC 00:10（cron `10 0 * * *`），以及手动 `workflow_dispatch`。权限是 `contents: write`。

第一个作业比较 `github.repository` 是否等于 `MaaXYZ/MaaPracticeBoilerplate`。只有模板仓库会得到 `should_run=true`。其他仓库，包括本仓库，打印跳过原因后结束，不会改 `deps/tools`。

模板仓库上它会下载这四个文件到 `deps/tools/`：

- `interface.schema.json`
- `interface_config.schema.json`
- `interface_import.schema.json`
- `pipeline.schema.json`

有变化时以 `github-actions[bot]` 提交，说明里带 `[skip changelog]`。`custom.action.schema.json` 和 `custom.recognition.schema.json` 不在下载列表中。本仓库要更新 schema 时需要自己替换 `deps/tools` 里的文件。
